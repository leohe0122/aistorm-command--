# 证据台账设计方案（AI 原生改造 · 第 0 步）

状态：待确认 · 2026-10-11

## 1. 要解决的问题

现在客户和商机的“事实”分散在 14 张表里，而且大多是人直接填的结论：

| 现有表 | 存的是什么 | 问题 |
|---|---|---|
| `meddpicc`、`opportunity_meddpicc` | 8 个维度的分数 + 备注 | 分数由人填写，备注里的依据无法逐条追溯 |
| `meddpicc_logs`、`meddpicc_snapshots` | 分数变化记录 | 只记分数变化，不记因为哪条事实而变 |
| `three_why`、`pain_metrics`、`competition_map`、`go_no_go` | 3 Why、痛点价值、竞争、门控 | 每张表各自有 evidence 文本字段，口径不一 |
| `key_contacts`、`relationship_coverage`、`opportunity_participants` | 关键人、覆盖、项目参与人 | 立场与角色是人填的判断，没有出处 |
| `customer_purchase_signals` | 客户原话 + 说话人 + 时间 + 来源 | **已经是证据形态**，可作为新模型的原型 |
| `meeting_minutes.aiFullSignals` | AI 从拜访提取的候选事实 | 确认后写进上面各表，原始证据随之丢失 |
| `intelligence_signals` | 外部情报 | 与客户事实分开存放 |

结果是：同一件事可能在三张表里有三种说法；AI 每次研判都要把这些表重新拼一遍；分数无法回答“为什么是 50 分”。

## 2. 核心原则

1. **证据是唯一的事实来源。**人和 AI 都只往台账里加证据（或确认、驳回证据），不直接改分数。
2. **判断由证据推导。**MEDDPICC、Win 五因子、3 Why、Go/No-Go、关系覆盖都是“评估”，由规则或 AI 基于已确认证据计算，每个结论都带引用的证据编号。
3. **AI 提取的内容先是候选。**人确认后才成为事实，延续现在“未确认不写入”的边界。
4. **保留人工否决权。**管理者可以覆盖某项评估，但必须写理由，并与 AI 结论并列显示。

## 3. 数据模型

### 3.1 `evidence`（证据）

| 字段 | 说明 |
|---|---|
| `id` | |
| `clientId` / `opportunityId` | 归属客户；商机相关时填商机（沿用现有按角色可见范围） |
| `kind` | `statement` 客户原话 / `observation` 我方观察 / `document` 文件内容 / `external` 外部情报 |
| `claim` | 一句话事实陈述，例如“CIO 刘明是最终签字人” |
| `quote` | 原话或原文片段（可为空） |
| `subjectName` / `contactId` | 事实涉及的人 |
| `topics` | 标签数组：`M`、`E`、`D1`…`C2`、`pain`、`why_now`、`trigger`、`competitor`、`budget`、`timeline` 等 |
| `polarity` | 对我方赢单：`positive` / `negative` / `neutral` |
| `occurredAt` | 事实发生时间（区别于录入时间） |
| `sourceType` / `sourceId` / `sourceExcerpt` | 来源：拜访、邮件、电话、文件、AI 引导问答、外部情报、手工录入；指回原始记录 |
| `status` | `candidate` 待确认 / `confirmed` / `rejected` / `superseded` |
| `supersedesId` | 新事实替代旧事实时指向旧记录（例如预算从“未批”变为“已批 200 万”） |
| `confidence` | AI 提取时的把握程度 |
| `createdBy` / `confirmedBy` / `confirmedAt` | 人或 AI；确认人 |
| `aiRunId` | AI 提取时对应的调用记录 |

### 3.2 `assessments`（评估）

| 字段 | 说明 |
|---|---|
| `scope` / `targetId` | `client` 或 `opportunity` |
| `framework` / `dimension` | 例如 `meddpicc` / `E`，`win` / `Champion`，`go_no_go` / `gate4` |
| `score` | 分数（沿用现有量纲） |
| `rationale` | 一两句理由 |
| `evidenceIds` | 支撑该结论的证据编号 |
| `computedBy` | `rule` 或 `ai`（附 `aiRunId`） |
| `override` / `overrideReason` / `overrideBy` | 人工覆盖 |
| `stale` | 有新证据进入后标记为待重算 |

### 3.3 `ai_runs`（AI 调用记录）

记录每次 AI 调用的功能名、提供方、模型、提示词版本、耗时、Token、成功或失败。用途有三个：给每条 AI 结论留出处；统计成本；评测与线上表现对照。

## 4. 数据如何流动

```
原始素材（拜访记录 / 邮件 / 文件 / AI 引导问答）
  → AI 提取 → evidence(candidate)
  → 人确认或修正 → evidence(confirmed)
  → 受影响的 assessments 标记 stale → 规则 / AI 重算（带证据引用）
  → 页面、主动提醒、对话入口都只读 assessments 与 evidence
```

## 5. 迁移步骤（每步可单独上线）

1. **建表，双写。**新建三张表；现有拜访信号确认、购买信号录入、AI 引导确认这三条写入路径同时写入 `evidence`。页面不变。
2. **评估上线。**新增 `assessments` 计算；计算结果同时回写旧表的分数字段，旧页面照常显示，但分数旁可展开查看证据。
3. **切换读取。**商机作战室、客户作战台、AD 指挥中心改读 `assessments`；手工填分入口改为“补充证据”。
4. **下线旧写入。**旧表只作为只读视图保留一段时间，确认无依赖后删除。

## 6. 需要确认的事项

1. **现有模拟数据怎么处理？**建议不做复杂的历史迁移，而是用新模型重新生成一套模拟数据（同时作为评测用例来源）。现有 `customer_purchase_signals` 可直接转换。
2. **分数量纲是否保持不变？**现在客户级 MEDDPICC 是 0-100、商机级是 0-4、Win 因子是 0-100。建议统一为 0-100，展示层再换算。
3. **谁可以确认证据？**建议：录入人本人与 AD 可确认；SA 只能确认与技术评估相关的证据。
